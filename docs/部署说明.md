## 4. 与原始文档的关键差异（重要）

### 4.1 SnowLuma 必须放在工作区外 —— 否则注入必失败

**这是本次部署遇到的最大坑，原文档没有提到。**

原文档让解压到任意位置即可，但本机 `D:\some-project` 目录被施加了 Windows
**低完整性级别（Low Mandatory Level）标签**，且带 `(OI)(CI)` 继承，导致里面所有文件
（包括新建的）都被标记为 Low。

后果：
- SnowLuma 以 Low 完整性运行 → 无法向 Medium 完整性的 QQ 进程注入 DLL
- 报错 `component loading failed [COMPONENT_LOAD_FAILED]`
- 且无法写 `%TEMP%`，连带 `login.db` 读取失败（`EPERM: mkdtemp`）

**解决方法**：把 SnowLuma 复制到 `D:\SnowLuma`（D 盘根目录无该标签），
复制操作不保留 SACL，文件恢复为未标记 → Medium 完整性 → 注入正常。

验证方法（启动日志中应出现）：
```
Node integrity: process=Medium (RID=8192); EXE=unlabeled
```
若显示 `process=Low` 或 `EXE=Low`，注入一定失败，请重新复制到无标签路径。

自查标签的命令：
```powershell
icacls "路径" | Select-String "Mandatory"
```

### 4.2 Node 版本

SnowLuma v2.2.0 要求 Node `^24.22.1 || >=26.12.1`，而系统 PATH 里的 node 是
**v22.17.1**，直接跑 `launcher.bat` 会版本检查失败。

解决：发布包自带 `node.exe` v24.22.1，启动脚本已改为显式调用 `.\node.exe`。

### 4.3 适配器必须配 token

原文档说「token 都留空亦可」，但 **SnowLuma v2.2.0 的 WS 服务器强制校验 token**，
留空会返回 `401 Invalid response status` 并无限重连。

解决：从 `D:\SnowLuma\config\onebot_<QQ号>.json` 的 `wsServers[].accessToken`
取出 token 填入适配器 `[client] token`。

### 4.4 EULA 哈希

原文档 §3.2 的两个哈希经实测**完全正确**，可直接用：
```
EULA_AGREE=8e6e7d647f7f82d6ea98456b73908656
PRIVACY_AGREE=91e5db7659c560bc3545e63859b6ebc0
```

## 5.5 人格与表情包（2026-10-26 追加）

### 人格化改造

`bot_config.toml` 的 `[personality]` 已从原来的一句话身份，扩成四层结构：

| 字段 | 作用 | 改造要点 |
|---|---|---|
| `personality` | 她是谁 | 20 岁大二视传女生，嘴直心软、有点傲娇、情绪真实、不讨好 |
| `behavior_style` | 何时说话（读空气） | 给出唯一判断标准「接这句话是让对话更有意思，还是打断别人」；不确定时默认不说 |
| `reply_style` | 怎么说话 | ≤25 字、口语、可省主语、带语气词、不堆 emoji、不说教 |
| `multiple_reply_style` | 备用风格 | 6 种（敷衍/噎人/简短建议/玩梗/撒娇/只发一个词），`multiple_probability = 0.15` |

同时：
- `alias_names = ["小麦"]` —— 被叫「小麦」也算在叫它
- `group_chat_prompt` 增加**消息格式说明**：昵称与群名片可能是同一人的两个名字，别误判成两个人（对应原文档踩坑 #7）；并明确「什么时候不回」
- `private_chat_prompts` 强调别秒回一大段、不必随叫随到

> 全部改动走热重载，改完保存即生效，无需重启。

### 偷表情包

`steal_emoji` 本来默认就是 `true`，实测已自动偷到 6 张并打标。本次调整：

| 参数 | 原值 | 新值 | 原因 |
|---|---|---|---|
| `max_reg_num` | 64 | **200** | 64 张库容太小，很快被替换 |
| `emoji_send_num` | 25 | **30** | 候选池更大，挑得更准 |
| `content_filtration` | false | **true** | 过滤不合适内容（合规考虑，代价是每条多一次 LLM 调用） |
| `use_new_send_logic` | false | **true** | 让思考模型直接看图挑表情，贴合度更高 |

⚠️ `use_new_send_logic = true` 要求思考模型支持视觉，因此 `model_config.toml` 里
`flash-think`（planner 用的就是它）已设 `visual = true`。
代价：聊天里的图片会以图像形式进 planner 上下文，token 消耗上升。
若在意成本，把这两处改回 `false` 即可。

### 表情标签质量（踩坑 #4 的实证）

偷到 6 张后发现**6 张里有 5 张都标成「无语」**，几乎无区分度，这正是原文档踩坑 #4 描述的现象。

两步处理：
1. 重写 `prompts/zh-CN/emoji_content_analysis.prompt`，从「只提情绪」改为
   **主体 + 动作 + 出处/梗名 + 情绪 + 场景**，最多 8 个标签（原文件备份为 `.bak`）
2. 旧描述按哈希缓存不会自动更新，所以逐张看图后手动改写了这 6 条的描述，
   并全部注册进可发送池

改后示例：`二次元猫耳女孩,闭眼撇嘴,委屈,困,想哭` / `狸花猫,瞪眼张嘴,震惊,呆滞,离谱`，
不再是一堆「无语」。

> 以后新偷的表情会用新提示词自动打标，无需手动干预。

## 5.7 长期记忆（A_Memorix）——已启用，降级运行

`bot_config.toml` 里 `[a_memorix.plugin] enabled = true`。

**当前状态：稀疏检索（BM25/FTS5）+ 元数据写入模式。**

启动日志会看到：
```
[记忆内核] embedding 进入降级态，将启用 sparse-only 与 metadata-only 写入回退
[记忆稀疏检索] 稀疏索引预热完成: backend=fts5
```

这不是故障，是**已知且可用的降级路径**。含义：

| 能力 | 是否可用 |
|---|---|
| 记住聊过什么（文字段落） | ✅ 可以 |
| 关键词/中文分词检索 | ✅ 可以（FTS5 + 中文分词） |
| 人物画像、聊天摘要、人物事实写回 | ✅ 可以 |
| 语义近义检索（「电脑」能搜到「计算机」） | ❌ 不可用 |
| 图片相似度召回 | ❌ 不可用 |

**要补上向量检索**，需要任选其一：
1. 换一个**带 embedding 模型**的中转站（如 `text-embedding-3-small`、
   `bge-m3`），把该模型加进 `model_config.toml` 的 `[[models]]`（
   `model_type = "embedding"`），再把它的 `name` 填进
   `[model_task_config.embedding] model_list`。
2. 本地跑 embedding：`uv pip install sentence-transformers`，然后在 A_Memorix
   配置里指向本地模型（会占内存/显存，且首次要下模型）。

补齐后需重启 MaiBot，日志里降级态消失即为生效。

## 5.10 联网搜索 —— 怎么开

MaiBot 内置统一的 `web_search` / `web_fetch` 工具，支持 6 种服务：
`deepseek` / `tavily` / `exa` / `firecrawl` / `anysearch` / `stepsearch_mcp`。

**关键：这两个能力都不走你现在的中转站。** 实测你的两个中转站：

```
api2.example.com/v1/tools/search   -> HTTP 404
api.example.com/v1/tools/search -> HTTP 404
```

它们只代理对话模型，没有搜索端点。所以要另找一个搜索服务。

### 推荐：Tavily（最省事，有免费额度）

1. 去 https://tavily.com 注册，免费档每月 1000 次搜索，拿 `tvly-` 开头的 key
2. 在 `model_config.toml` 里加服务定义：

```toml
[web]
preview_chars = 4000
services = { tavily = { adapter = "tavily", api_key = "<YOUR_API_KEY>" } }
```

3. 同一个文件里把功能分配填上（`model_list` 填**服务名**，不是模型名）：

```toml
[model_task_config.web_search]
model_list = ["tavily"]
```

4. 保存即热重载。之后麦麦就有 `web_search`（搜）和 `web_fetch`（读网页）两个工具了。

### 其他可选

| 服务 | adapter 值 | 备注 |
|---|---|---|
| Exa | `exa` | 语义搜索质量高，key 从 exa.ai 拿 |
| Firecrawl | `firecrawl` | 网页抓取强，适合 `web_fetch` |
| AnySearch | `anysearch` | 一次调用同时给摘要+正文 |
| DeepSeek 官方 | `deepseek` | 需要 DeepSeek 官方 key（不是中转站） |

> 实测：tavily / exa / firecrawl / anysearch 的官方地址**都能连通**（返回 400/401
> 而不是超时），所以只要拿到 key 就能直接用。

## 5.11 语音识别 —— 怎么开

`bot_config.toml`：

```toml
[voice]
enable_asr = true
```

但**光开开关没用**，它还要一个能转写音频的模型。MaiBot 走的是标准 OpenAI
`/audio/transcriptions` 接口（代码见 `src/llm_models/model_client/openai_client.py`
的 `audio.transcriptions.create`）。

**实测你的两个中转站都不提供这个接口**：


## 5.12 读写文件 / 控制电脑 —— 权限范围怎么设

这块是 `[agent]` 段控制的，**目前整体关闭**（`enabled = false`），
麦麦完全碰不到你的文件系统。

如果你以后想开，MaiBot 的设计本身带隔离：

| 配置项 | 作用 | 建议 |
|---|---|---|
| `enabled` | 总开关 | 默认 `false`，想开再开 |
| `computer_tools` | 给 Agent 桌面操作（鼠标键盘、截图） | **建议永远 `false`**，风险最高 |
| `networking` | 沙盒内是否联网 | 按需，默认 `true` |
| `memory_mb` | 沙盒内存 | 4096 |
| `acp_cwd` | 外部进程工作目录 | 留空 = `data/agent/workspace`，**别指向 D:\ 根或用户目录** |

要点：
- 文件操作跑在**沙盒**里，默认工作区是 `MaiBot\data\agent\workspace`，
  不是你的真实 D 盘。
- `acp_cwd` 是唯一能「逃出」沙盒指向真实目录的入口，**保持留空或指向专用空目录**。
- `[mcp.client.roots]` 目前 `enable = false`、`items = []`，
  表示不向外部工具暴露任何真实目录 —— **保持这个状态**。

**我的建议**：如果你只是想让麦麦「会聊天、会玩梗、会发表情包」，
这块就**一直关着**。开着它等于给一个跑在 QQ 群里的模型对本地文件的读写权限，
群友一句提示词注入就可能诱导它读敏感文件。真要开，也应该：
1. 先建一个空目录专门给它用，`acp_cwd` 指过去
2. 只在该目录里放允许它看的东西
3. `computer_tools` 保持 `false`（不给鼠标键盘）

## 5.13 人设 / 长期记忆 / 跨对话记忆 —— 实况说明

### 人设是什么

人设写在 `bot_config.toml` 的 `[personality]` 段，共 5 个字段：

| 字段 | 作用 | 当前内容摘要 |
|---|---|---|
| `personality` | 她是谁 | **麦麦**，20 岁，大二，学视觉传达。友善、脾气好、说话软但不黏，被夸会不好意思 |
| `behavior_style` | 什么时候说话 | 看气氛；被 @ 优先回；有人求助或情绪低落优先接且放软；不确定就不说 |
| `reply_style` | 怎么说话 | 简短口语、≤25 字、软语气词「呀啦吧嘛」、不说教、不同意先说「我觉得吧」 |
| `multiple_reply_style` | 6 种随机变体 | 敷衍、小抱怨像撒娇、认真给建议、玩梗、关心「你还好吧」、懒得打字 |
| `multiple_probability` | 变体触发概率 | `0.15` |

别名：`alias_names = ["小麦"]`，别人叫「小麦」她也认。
群聊/私聊还各有一套 `group_chat_prompt` / `private_chat_prompts`。

### 长期记忆 —— 有，但很浅

`[a_memorix.plugin] enabled = true`，**已实际工作**。查数据库确认：

| 表 | 内容 | 行数 |
|---|---|---|
| `person_profile_snapshots` | **人物画像**（每个聊过的人一份） | **6** |
| `paragraphs` | 记忆段落 | 0 |
| `chat_summary_checkpoints` | 聊天摘要进度点 | 2 |
| `image_assets` / `image_observations` | 图片记忆 | 1 / 1 |
| `episodes` / `relations` / `fact_claims` | 事件/关系/事实 | 0 |

**真人名已经记下来了**：`清浅`、`莫小邪`、`Zeory45` 等 6 个人的画像已在库。

但**画像内容是空的**：
> 画像内容示例（引用块，避免被当成标题）：
> # 人物画像
> ## 身份设定
> - 暂无
> ## 关系设定
> - 暂无
> ## 稳定了解
> - 暂无
> ```
只有名字，没有「他是个什么人」。原因见下。

### 为什么记得浅

1. **向量检索降级**：两个中转站没有 embedding 模型，`paragraphs` 写入走
   metadata-only 回退，所以 0 条段落。语义检索这条路是断的。
2. **写回阈值较高**：`chat_summary_writeback_message_threshold = 36`，
   要累计 36 条才写一次摘要；`person_fact_writeback_enabled = true` 但需要
   LLM 提取到明确事实才落库。
3. **总消息量还少**：全部会话加起来 223 条，摊到 5 个会话上，样本不足以
   形成有内容的画像。

**结论**：机制是通的，属于「刚开伙、还没积累」。正常聊几天，
`paragraphs` 和画像会逐渐长起来。

### 跨对话记忆 —— **目前是隔离的**

这是关键区别，别混淆：

| 能力 | 状态 | 开关 |
|---|---|---|
| 在**同一个群/私聊**里记得之前聊过什么 | ✅ 有 | 上下文 + 该会话的长期记忆 |
| 知道每个人的**人物画像**（跨会话） | ✅ 有 | `enable_person_profile_injection = true` |
| **A 群的记忆能被 B 群检索到** | ❌ **没有** | `global_memory_sharing_enabled = false` |
| 启发式跨聊天流召回 | ❌ 关闭 | `heuristic_memory_cross_chat_enabled = false` |
| 私聊里拉起群聊记忆 | ❌ 关闭 | `heuristic_memory_group_to_private_enabled = false` |
| 群聊里拉起私聊记忆 | ❌ 关闭 | `heuristic_memory_private_to_group_enabled = false` |

也就是说：
- 你在私聊里跟她说的事，**不会**出现在她在群里聊天时的记忆检索里
- 群 A 的聊天内容，**不会**被群 B 的对话检索到
- 但**人物画像例外**——`人物画像`是按人存的，她在任何会话里都能识别
  「清浅是谁」，并自动注入当前对象画像

### 想开跨对话记忆怎么办

改 `bot_config.toml`：

```toml
[a_memorix]
global_memory_sharing_enabled = true   # 让普通记忆查询在所有聊天流里检索
```

或者更精细地只共享指定的几个会话：

```toml
[a_memorix]
shared_memory_groups = [["群1的session_id", "群2的session_id"]]
```

> ⚠️ 全部开 `global_memory_sharing_enabled = true` 有隐私问题：
> 如果你在私聊里说了私事，她在群聊时理论上能检索到。
> 建议用 `shared_memory_groups` 精确控制，或者只开
> `heuristic_memory_group_to_private_enabled`（群里的话能在私聊提）。

## 5.16 群里不爱说话 —— 根因与修法

### 症状

日志显示她在新群 `群D` 里连续 7 次决定不回复：

```
[空闲退避] [群D] 空闲退避 来源=planner 连续=7次 等待=120s
```

`stop` 14 次、`reply` 6 次。

### 两个原因

1. **提示词太克制**：`behavior_style` 里写了「不确定要不要说话时，默认不说」「连着被无视就安静一会儿」，
   等于教她保守。
2. **退避算法太狠**：`start_count = 1` 意味着**第 1 次不回复就开始退避**，
   且 `cap = 120` 秒。一旦连续沉默，她会「消失」两分钟。

### 修法

**提示词**（`behavior_style` 改写）：
- 「不确定时倾向于接一句短的开个玩笑，而不是沉默」
- 「大约一半的机会开口」
- 删掉「默认不说」

**退避参数**：

| 配置 | 原值 | 新值 |
|---|---|---|
| `no_action_backoff_base_seconds` | 8.0 | 6.0 |
| `no_action_backoff_cap_seconds` | 120.0 | **40.0** |
| `no_action_backoff_start_count` | 1 | **3** |
| `no_action_backoff_bypass_pending_count` | 6 | **4** |

效果：前两次不回复不降温，第 3 次才退避，最长只等 40 秒；有 4 条新消息立即打断等待。

### 验证

重启后日志：

```

[麦麦推理引擎] [群D] 工具=reply
```

## 5.19 模型故障转移调优 —— 超时立刻换供应商

### 模型身份确认（全部是 deepseek-v4.1-flash）

| 模型别名 | model_identifier | 供应商 |
|---|---|---|
| `flash-chat` | **deepseek-v4.1-flash** | codexpert |
| `flash-think` | **deepseek-v4.1-flash** | codexpert |
| `flash-vision` | **deepseek-v4.1-flash** | codexpert |
| `geili-chat` | **deepseek-v4.1-flash** | geili |
| `geili-think` | **deepseek-v4.1-flash** | geili |
| `geili-vision` | **deepseek-v4.1-flash** | geili |

六个别名指向同一个模型，只是供应商和 reasoning 开关不同。**没有任何 pro 模型。**

### 原问题

日志里大量出现：

```
任务 'maisaka.replyer' 的模型 'flash-chat' 触发硬超时 240.0s → 切换到下一个模型
任务 'A_Memorix.ChatSummarization' 模型 'flash-chat' 触发硬超时 240.0s
```

原因：`max_retry = 3` × `timeout = 180`，再排 4 个模型，
**最坏情况一次请求要等 3×180×4 ≈ 36 分钟**。表现出来就是她「消失」很久才回。

### 改法

**重试策略**（两个 provider 都改）：

| 参数 | 原值 | 新值 | 含义 |
|---|---|---|---|
| `max_retry` | 3 | **1** | 失败一次就换供应商，不原地重试 |
| `timeout` | 180 | **60** | 单次请求 60 秒封顶 |
| `retry_interval` | 4 | **2** | 真要重试时只等 2 秒 |

> 代码依据：`src/llm_models/utils_model.py` 第 1056-1058 行
> `retry_remain = max(1, retry_limit)`，`max_retry=1` 即为「只试一次」；
> 第 1472 行 `ModelAttemptFailed` 直接 `continue` 到下一个模型。

**模型链缩短**（每个任务从 4 个减到 2 个，两家互为备份）：

| 任务 | 原 model_list | 新 model_list |
|---|---|---|
| `replyer` | flash-chat, flash-think, geili-chat, geili-think | **flash-chat, geili-chat** |
| `planner` | flash-think, flash-chat, geili-think, geili-chat | **flash-think, geili-chat** |
| `memory` / `utils` / `learner` / `fast_model` / `emoji` | 4 个 | **flash-chat, geili-chat** |
| `vlm` | flash-vision, flash-think, geili-vision, geili-think | **flash-vision, geili-vision** |

**效果对比**：

| | 原来 | 现在 |
|---|---|---|
| 第一供应商超时 | 等 180s×3 后才换 | **60s 后立即换** |
| 最坏总等待 | ~36 分钟 | **约 2 分钟** |

实测重启后：`超时次数: 0`，工具调用正常（`reply` 8 次 / `show_emoji_list` 1 次）。

> 实测供应商延迟波动大（codexpert 偶尔 502 / 8-13 秒，geili 稳定 3-5 秒），
> 所以自动切换是必要的，不是可选项。

```python
if raw_visibility in {"visible", "deferred", "hidden"}: return raw_visibility
if bool(entry.metadata.get("core_tool", False)): return "visible"
```

## 5.25 表情包发不出去 —— 真正的根因

### 现象

`show_emoji_list` 调了 5 次，`select_emoji` 只有 1 次，
**`attach_emoji` 一次都没填过**。

### 追踪每次 show_emoji_list 之后的动作

```
17:16:52  show_emoji_list → stop      ← 看完就放弃
17:21:27  show_emoji_list → reply     ← 回了文字，没填 attach_emoji
17:24:46  show_emoji_list → stop      ← 又放弃
17:29:12  show_emoji_list → select_emoji   ← 唯一成功的一次路径
18:09:11  show_emoji_list → reply     ← 还是没填
```

### 工具真实职责

从 planner 记录里读出的官方描述：

| 工具 | 描述 |
|---|---|
| `show_emoji_list` | 查看随机抽取的表情包选择拼图。图片会进入你的上下文，**不会发送给聊天对象**。调用 reply 时将选中图片的序号填入 attach_emoji |
| `select_emoji` | 根据当前对话情绪从表情包库中选择并发送合适的表情包（另一条独立路径） |

所以：**`show_emoji_list` 只是「看一眼」，不发图**，必须在 `reply` 里填
`attach_emoji=序号` 才真的发。她经常看完就 `stop`，或者回了文字但忘了填序号。

### 修法：把这一步写死

`[personality].reply_style` 改为：

> 你很喜欢发表情包，而且真的会发出去。做法是固定的两步：第一步调
> show_emoji_list 看候选拼图；第二步在 reply 里**必须**填 attach_emoji 序号，
> 图才会跟着文字一起发。注意：只调 show_emoji_list 不填 attach_emoji，
> **等于白看，图发不出去**；也别看完就 stop。

群聊提示词里同样强调「务必两步走」。

> ⚠️ 这不是参数问题。`emoji_send_num` 只控制拼图里放几张，
> **完全不影响发不发**。决定权在模型有没有填 attach_emoji。

## 5.26 回复延迟诊断 —— 结论与直觉不同

### 用 1100 条真实收发记录算延迟

| 指标 | 值 |
|---|---|
| 中位数 | 15 秒 |
| 平均 | **44 秒** |
| P90 | **136 秒** |
| 最慢 | 384 秒 |
| >60 秒 | 263 条 |

看着很糟。但拆开看就不一样了。

### 拆分「决定回复」和「决定不回复」

```
实际发出回复: 16 次   延迟中位数 6s  平均 5s  P90 7s  最慢 8s
决定不回复  : 10 次   （Planner 选了 stop）
```

**真实回复链路只要 5–8 秒。** 统计里那些 136 秒、384 秒的长尾，

## 5.27 多 API Key 并发 —— 实测不建议

### 先做了并发压测

对两家供应商分别打 1 / 4 / 8 个并发请求：

| 并发 | codexpert | geili |
|---|---|---|
| 1 | 1/1 成功 6.6s | 1/1 成功 4.3s |
| 4 | 4/4 成功 5.6~7.6s | 4/4 成功 2.4~4.6s |
| 8 | **8/8 成功** 5.5~8.6s | **8/8 成功** 2.1~5.6s |

**没有任何限流。** geili 并发 8 个时反而更快（2.09s）。

### 为什么会有「并发受限」的错觉

上游两个供应商用的都是同一套 `deepseek-v4.1-flash`。
真实瓶颈看日志是**串行等待**，不是被限流：
单次 6~8 秒，一条接一条走，8 条消息自然要 50 秒往上。

### 加 Key 的实际问题

1. **配置结构不支持** —— `APIProvider.api_key` 是单个字符串字段
   （`src/config/model_configs.py:37`），填不了数组。要做负载均衡得改主程序。
2. **不解决真实瓶颈** —— 实测没有限流，加 Key 等于白加。
3. **收益低风险高** —— 要改核心代码，还得自己实现轮询/健康检查/失败转移，
   而这些 `model_config` 本来就有（`max_retry` + 多模型列表）。

### 已经有的等效能力

现在的配置已经实现了「第一个 key 挂了自动切第二个」：

```toml
[provider.codexpert]  max_retry = 1   # 超时试 1 次就换
[provider.geili]      max_retry = 1

[model_task_config.replyer]  models = ["flash-chat", "geili-chat"]
[model_task_config.planner]  models = ["flash-think", "geili-chat"]
```

—— 按任务分配不同模型，失败了自动走下一个。这就是「多 Key 并用」想要的效果。

> 如果你确实有第三个 key 想加进来，最省事的做法是**新建一个 provider**，
> 然后把它追加到各任务列表末尾当第三备份。不用改代码。

### 正确做法：设成极小正数

```toml
{platform="qq", item_id="300000004", rule_type="group", time="00:00-23:59", value=0.02}
```

原理是 `src/chat/utils/utils.py:249`：

```python
if is_at and reply_timing_config.inevitable_at_reply:
    reply_probability = 1.0    # 被 @ 时强制 100%，覆盖 talk_value
```

而 `scheduler.py:85` 的 `_has_forced_turn_trigger()` 会在动态门控之前拦下，
被 @ 的消息**不受低频率影响**。

### 实测生效值

```
300000002   0.35   35.0%   群E（490人）
```

## 5.32 修一个真 bug：内部格式标签泄漏到聊天

### 现象

SnowLuma 日志里她发了这些：

```
18:43:01  发送：<message msg_id="-300000016" user="十二月">
18:43:19  发送：<message msg_id="300000015"
18:43:21  发送：user="十二月">
```

### 根因

`<message ...>` 是 **Planner 给模型看的上下文格式**，
由 `src/maisaka/context/planner_messages.py:48` 生成：

```python
message_attrs.append(f'msg_id="{escape(to_display_message_id(message_id), quote=True)}"')
```

deepseek-v4.1-flash 在上下文里看到这个格式，偶尔会**照着模仿**，
把格式模板当成正文输出，于是泄漏成真实聊天消息。

### 修法

`[personality].reply_style` 末尾追加：

> 你回复时只说人话。聊天记录里那些 `<message ...>`、`user=...`、`msg_id=...`
> 是系统给你的内部格式，绝对不能写进你的回复，也不要模仿这种写法。

### 改配置时的一个坑

往 TOML 双引号字符串里塞内容，**文本本身不能含未转义的双引号**。
第一次写 `user="..."` 直接把第 30 行截断了，报
`TOMLDecodeError: Expected newline or end of document`。
已备份 `.bak11` 回滚后改成 `user=...`（不带引号）才成功。

> 这是配置损坏，不是运行时错误——**改完必须 `tomllib.load` 验证一次**。

## 5.39 私聊审计 —— 问题清单

### 数据（76 条私聊，5 个对话对象）

| QQ号 | 昵称 | 收到 | 回复 | 完全未回 |
|---|---|---|---|---|
| 300000011 | — | 38 | 51 | 9 |
| 300000010 | — | 11 | 16 | 0 |
| 100000003 | 小号A | 3 | 4 | 1 |
| 100000000 | 十二月 | 15 | 20 | 1 |
| 300000008 | — | 9 | 13 | 0 |

### 延迟分布（按「这条消息 -> 该用户收到下一条回复」算）

```
中位数 15s    P75 70s    P90 252s    最慢 1462s
>60s  19 条      >180s  9 条
```

**中位数 15 秒是健康的。问题是长尾**——有 19 条超过一分钟。

### 长尾的三个原因

**原因 1：`reply` 空转重试（最主要）**

日志里反复出现：

```
18:23:09 [正文工具调用] 工具=reply
18:23:12 回复工具未生成可见消息，将继续下一轮循环
18:23:15 工具=reply
18:23:18 回复工具未生成可见消息，将继续下一轮循环
...连试 4 次...
18:23:32 工具=wait
18:24:32 等待结束，再看一眼！   ← 等了 60 秒
18:24:40 deepsleep: 唔…这话说得也太满啦     ← 终于回了
```

一条消息从 18:20:28 拖到 18:24:40，**耗时 4 分钟**。

全日志统计「回复工具未生成可见消息」：run9 有 10 次、run15 有 6 次。

> 这个不是纯故障。`reply` 有时会生成不可见的中间产物（比如只出思考不出正文），
> 系统会重试，重试多了就慢。**根因还是模型输出不稳定。**

**原因 2：主动 `wait` 等待**

私聊 157 次工具调用里，`wait` 占 21 次（13%）。
`wait` 默认等 60 秒，期间不回话。

**原因 3：`wait` 之后选了 `stop`**

`和我谈` 那条（16:59）最典型：

```
工具=wait  →  等待结束，再看一眼！  →  工具=stop
```

她等了 60 秒，然后决定不回了。最终这条消息 1462 秒后才等到一个不相关的回复。

### `stop` 比例偏高

```
私聊工具调用 157 次：
  reply  83 (52%)
  stop   43 (27%)   ← 每四次决策就有一次是「不说话」
```

## 5.44 思考预算与 token 实测

### 真实消耗

| 任务 | 输入 | 输出 | 耗时 | 输出/输入 |
|---|---|---|---|---|
| planner | 中位 7131 / 平均 6795 | 中位 224 / 平均 228 | 中位 8.1s | **3.4%** |
| replyer | 中位 1874 / 平均 2028 | 中位 11 / 平均 28 | 中位 3.0s | **1.4%** |

**单次决策约 7K 输入 + 230 输出 = 7.2K tokens。**

### 发现的问题：两个 think 模型预算不一致

```toml
# 改前
geili-think:  extra_params = {thinking = {type = "enabled"}, reasoning_effort = "high"}
geili2-think: extra_params = {thinking = {type = "enabled", budget_tokens = 4000}, reasoning_effort = "high"}
```

**`geili-think` 没有预算上限**，`geili2-think` 是 4000。
主备切换时思考量会突变，长尾延迟部分源于此。

改后统一为 `budget_tokens = 4000`。

### 预算该设多少：结论是不用调

理由：

1. **实测输出平均 228 tokens，远低于 4000 上限** —— 预算根本没被用满，
   调低只会压缩复杂判断的空间，没有收益。
2. **真正的成本在输入，不在思考**。单次 7K 输入里绝大部分是系统提示词
   （人设 + 行为准则 + 工具定义 + 聊天历史），输出只占 3.4%。
   想省钱该减上下文，不是减思考。
3. **思考质量直接影响 stop 率**。planner 要判断「该不该说话」，
   压缩思考会更容易误判成 stop。

**建议保持 4000。** 如果哪天觉得她判断变笨了，可以升到 6000；
不建议降到 2000 以下。

> 真正的优化方向：planner 输入稳定在 7K 以上，缓存命中率 85%~90% 时
> 实际成本已很低。不必为了省钱动思考预算。

## 5.46 表情包注册积压 bug（重要）

### 现象

私聊让「存一下这些表情包」，她回「存好啦存好啦」，但发不出来。
后来用 `select_emoji` 发了个相似图，还老实承认「图片库里没这个原图」。

### 三重原因

**原因 1：根本没有「保存表情包」工具**

内置工具清单：

```
wait / stop / reply / query_memory / send_emoji
show_emoji_list / tool_search / subagent / subagent_status / subagent_stop
```

只有 `show_emoji_list`（看）和 `send_emoji`（发），**没有「存」**。
`register_emoji_to_db` 是内部函数，未暴露为工具。
所以她说「存好啦」是**编的**，实际啥也没做。

**原因 2：自动偷表情只做到了「缓存」，没做到「注册」**

数据库实测：

```
image_type=EMOJI 总记录 118
  已注册  55
  未注册  63   ← 文件在本地、描述也在，就是发不出去
```

`is_registered=0` 的记录不进入可发送池。

**原因 3：巡检每轮只注册一个（真正的 bug）**

`emoji_manager.py:1194`：

```python
if register_status == "registered":
    break          # ← 每轮只注册一个就退出
```

`check_interval = 10` 分钟，**一小时最多注册 6 个**。
而偷表情是随消息实时进行的，产出速度远超 6 个/小时 → 持续积压。

时间线证据：

```
21:05:45  你的表情包 A 被缓存（is_registered=0）
21:05:55  你的表情包 B 被缓存（is_registered=0）
21:13:56  巡检开始
21:14:00  只注册了 B          ← break 了
          A 一直挂着，所以发不出来
```

### 修复

**改代码**：把 `break` 改成按批计数：

```python
_MAINTENANCE_REGISTER_BATCH = 20
registered_this_round = 0
...
if register_status == "registered":
    registered_this_round += 1
    if registered_this_round >= _MAINTENANCE_REGISTER_BATCH:
        logger.info(f"[emoji_maintenance] 本轮已补注册 {registered_this_round} 个，余下的下轮继续")
        break
```

**补数据**：直接改库把 62 条积压记录置为已注册。

```
补注册 62 个（文件缺失 0，无描述 0，封禁 0）
现可发送表情包: 118 / 总记录 118
```

重启后验证：

```
[表情包] [数据库] 成功加载 118 个已注册表情包
```

### 遗留

「让她手动存某个表情包」仍然做不到，因为**没有这样的工具**。
想做需要给主程序加一个新工具（`save_emoji`），需要改核心代码。
好消息是：别人发的表情包**现在已经会被自动偷并注册**，只是不能按指令点名存。

## 5.47 思考预算：结论是保持 4000

### 实测利用率

```
planner 输出中位数 150 tokens，最大 352      ← 上限 4000，用了 3.8%，峰值 8.8%
输入中位数 7282 tokens（主要是人设+工具定义+聊天历史）
```

**预算远远没用满。**

### 关于「她要读历史消息和记忆」

这是输入侧，不是思考侧：

| 内容 | 归属 | 规模 |
|---|---|---|

| 工具定义（10 个工具） | 输入 | ~2K |
| 聊天历史 + 记忆检索结果 | 输入 | 3~4K |
| **思考过程（reasoning）** | 输出 | **~150** |

**思考预算管不到「读多少历史」**，那只受 `cache_window`、历史条数、

该查的记忆不查、该用工具不用。

那时候从 4000 提到 6000，而不是无脑拉高。

> 当前判断质量的问题（stop 25%、reply 空转）根源不在预算，
> 而在上游模型输出不稳定。加预算解决不了。

## 5.55 表情包不爱发的真正原因

### 数据

近四轮统计：

```
总决策 257 次
实际发出表情包 5 次（1.9%）
show_emoji_list 调用仅 3 次
```

### 根因：引导写在了错误的位置

MaiBot 的提示词分两层，**各自给不同的模型读**：

| 配置项 | 谁读 | 用途 |
|---|---|---|
| `behavior_style` | **Planner** | 决定「这一轮做什么动作」——reply / stop / wait / show_emoji_list |
| `reply_style` | **Replyer** | 决定「这句话怎么说」 |

原来表情包的引导**全写在 `reply_style` 里**：

> 你很喜欢发表情包，而且真的会发出去。做法是固定的两步：
> 第一步调 show_emoji_list……

**但 Planner 根本读不到这段。** 它读的是 `behavior_style`，
那里一个字都没提表情包。

后果：Planner 不知道要发表情包 → 不会调 `show_emoji_list`
→ Replyer 阶段再怎么叮嘱「要发图」，`attach_emoji` 也填不进去了
（`attach_emoji` 只能由 Planner 在调 `reply` 时填）。

### 验证

实测 Planner 的系统提示词：

```
改前：
  含 show_emoji_list: True    ← 只是工具定义存在
  含「很喜欢发表情包」: False  ← 引导语读不到
  含「每三四次」      : False

改后：
  含「先调 show_emoji_list」: True
  含「每三四次」            : True
  含「只调前者不填序号」    : True
```

### 修复

**1. 把引导搬进 `behavior_style`（Planner 可见）**

```
【表情包】你爱用表情包，很多时候一个表情比打字更到位。
想发表情包时，动作是固定的两步：先调 show_emoji_list 看候选拼图，
再在 reply 里填 attach_emoji 序号——**只调前者不填序号，图发不出去**，
看完就 stop 也等于白看。
无语、敷衍、得意、撒娇、答应、懒得解释、看热闹这几种场合，
优先配上表情包，大约每三四次回复里有一次就该带图。
```

**2. 私聊必答也搬进 `behavior_style`**

```
【私聊要回】私聊是对方专门来找你说话，默认就应该接。
只要不是明确的骚扰或刷屏，哪怕只回「嗯」「怎么啦」也比沉默强。
沉默在群里是不打扰，在私聊里是冷落。
```

**3. 精简 `reply_style` 里的重复段落**

原来说了两遍同一套规则，容易打架，也白占 token。
`reply_style` 从 1312 字降到 1093 字。

## 5.58 自主发言机制全解

她「开口」有两种完全不同的路径。

### 路径一：被动响应（有人说话时）

**触发链：**

```
收到消息
  -> 消息防抖（2-5 秒，等对方把话说完）
  -> 读空气（调度器）
       |-- @ 我？          -> 强制触发（inevitable_at_reply=true，必进 Planner）
       |-- 私聊？          -> 频率 1.000，必进 Planner（不走概率）
       |-- 群聊？          -> 按 talk_value 概率决定要不要进 Planner
  -> Planner 思考：调 reply / stop / wait / 图片 / 表情包
  -> Replyer 组织语言
  -> 发送
```

**群聊的频率控制：**

```toml
talk_value = 1.0     # 全局默认
enable_talk_value_rules = true

# 按群单独覆盖
300000001  -> 0.10
300000002  -> 0.30
300000003  -> 0.40
300000004  -> 0.05
300000005 -> 0.30
300000006  -> 0.30
300000009 -> 不在列表，走全局 1.0
```

**不回复后的退避**（避免反复打量每一条）：

```toml
no_action_backoff_base_seconds = 6.0        # 连续不回时的起步等待
no_action_backoff_cap_seconds = 40.0        # 最长等待
no_action_backoff_start_count = 3           # 连续 3 次不回后开始退避
no_action_backoff_bypass_pending_count = 4  # 积压 4 条就立刻重新处理
```

**实测比例：**

| 场景 | stop | reply |
|---|---|---|
| 群聊 | 41% | 49% |
| 私聊 | 37% | 51% |

### 路径二：主动发起（没人说话时）

由 MaiTrace 插件驱动，**分三种主动行为**。

#### A. 主动私聊

代码条件（`engine.py:401-431`，必须**全部**满足）：

| # | 条件 | 配置项 | 当前值 |
|---|---|---|---|
| 1 | 当前活动不是工作/学习/出行 | 硬编码 | — |
| 2 | 不在睡眠阶段，且精力足够 | `private_min_energy` | 30.0 |
| 3 | 该用户 `enabled` 且 `proactive_enabled` | `[life].profiles` | 你 + qyy |
| 4 | 不在该用户免打扰时段 | `quiet_start/end` | 23:00–08:00 |
| 5 | 当天次数未超上限 | `daily_proactive_max` | 你 1 次，qyy 2 次 |
| 6 | 距上次主动 ≥ 180 分钟 | `private_min_interval_minutes` | 180 |
| 7 | 对方最近 15 分钟没说话 | `private_silence_minutes` | 15 |
| 8 | 距上次尝试 ≥ 100 分钟 | 硬编码 20 倍 | — |
| 9 | 有可用的**生活契机** | `opportunities` 表 | 见下 |

**第 9 条是关键**：她要说的是「自己刚在做的事」，不是空招呼。
契机来自生活引擎——数据库里 `status=available` 且未过期的记录。

实测契机样例：

```
晚上在图书馆刷群聊，聊聊熬夜和小饥饿   [20:33 创建, 21:30 过期]
调色预设翻车现场                     [已过期]
傍晚从图书馆出来绕操场走两圈          [已过期]
```

**有效期只有 30–90 分钟**，所以经常「没素材可说」就不发。

#### B. 发 QQ 空间说说

```toml
post_enabled = true
post_cooldown_minutes = 120        # 两小时内不重复发
check_interval_minutes = 20        # 每 20 分钟检查一次
post_blocked_activities = ["sleeping","working","studying","eating","exercising"]
```

同样需要 `claim_public_opportunity()` 拿到未过期契机，
拿不到就直接 return（`routine.py:434-435`）。

#### C. 刷空间（看好友动态、点赞评论）

```toml
browse_enabled = true
browse_cooldown_minutes = 40
```

这个不依赖契机，所以**执行频率明显高于发说说**。实测日志里
她频繁给好友点赞评论，但自己一条都没发过——原因就是契机。

### 一句话总结

| 类型 | 谁触发 | 会不会主动说话 |
|---|---|---|
| 被动响应 | 别人发消息 | 会（群里约一半） |
| 主动私聊 | 生活契机 + 9 个条件 | 偶尔，攒够素材才发 |
| 发说说 | 生活契机 + 冷却 | 少（契机易过期） |
| 刷空间 | 定时 | 频繁（点赞评论） |

**她不会「定时来找你聊天」**，只会在有具体生活内容可说时才开口。
这是设计使然，不是坏了。

## 5.62 上下文会不会太长崩掉

### 结论：不会

MaiBot 有三层防护，且实测运行良好。

### 第一层：硬性消息条数上限

配置（`bot_config.toml`）：

```toml
max_context_size = 30            # 群聊
max_private_context_size = 60    # 私聊
context_compaction_summary_max_chars = 6000
```

代码（`src/maisaka/context/post_processor.py`）：

```python
TRIM_THRESHOLD_RATIO = 1.2     # 超过上限 1.2 倍就裁
TRIM_TARGET_RATIO = 0.2        # 裁到 20%
MIN_RETAINED_CHAT_MESSAGES = 5 # 至少留 5 条
```

实际生效值：

| 场景 | 触发裁切 | 裁到 |
|---|---|---|
| 群聊 | 36 条 | 6 条 |
| 私聊 | 72 条 | 12 条 |

**这是按消息条数算的硬上限，不是靠 token 估算**——所以上下文不可能无限增长。

### 第二层：滚动摘要

裁掉旧消息前，先用 utils 模型把它们压成一段摘要（≤6000 字）：

```
上下文压缩完成: 压缩=N 保留原文=M
```

这段摘要会一直跟着 Planner 请求走，所以砍掉原文不等于失忆。

实测已触发 **7 次**（run28 两次、run29 四次、run31 一次），全部成功，无一次异常。

### 第三层：长期记忆写回

`chat_summary_writeback_enabled = true`，每 36 条消息自动写回 A_Memorix：

```
聊天摘要自动写回成功: trigger=message_threshold total_messages=36
```

所以即使上下文被裁，重要内容也进了长期记忆库，下次可以检索回来。

## 5.67 Planner 提速 + 「已开口就说完」（2026-10-27 11:50）

### 一、Planner 延迟：中位 36.5s → 预期秒级

**实测数据（08:00-11:00，39 个轮次）**：中位 36.5s、p75 53.6s、p90 90.6s、最大 120.1s；
<10s 仅 5 次，>60s 有 8 次。上下文消息数中位 51、p90 146、最大 162。

**根因**：Planner 首位是 `geili-think`（`thinking.enabled` + `budget_tokens=4000` +
`reasoning_effort=high`），每次决策都在做长时间深度推理。这也解释了上游 60s 超时频发
（思考占满超时窗口）。

**改法**：

```toml
# model_config.toml
[model_task_config.planner]
model_list = ["geili-chat", "geili2-chat", "geili-think"]   # 快模型优先，think 兜底
hard_timeout = 120.0                                          # 180 → 120
```

配合 `behavior_style` 新增规则（Planner 层）：

```
【先说一句，再补充】想到什么就先把它说出去，别憋在心里等想周全。
一句话能表达的，立刻调 reply 说掉；如果还想补充、还想配表情包或者翻记忆，
说完之后可以继续下一轮再说。宁可分两条发，也不要为了想完美而让人等半分钟。
```

**取舍**：决策少一层深思，可能"接得没那么准"。若观察到变笨，把 `geili-think` 调回首位即可回滚。

### 二、已开口就说完（打断策略）

**原行为**：她正在准备主动开口时用户发来消息，`controller.py` 会 release 掉这次主动任务
（日志 `新的真实入站消息已结束主动轮次`）；同时 Planner 进行中的请求会被新消息打断重来。

**修改**（两处，覆盖所有打断来源）：

1. `runtime.py::_request_planner_interrupt_for_message` —— 若本回合已成功调用过 reply，
   直接跳过打断（新消息进缓存，下一回合处理）。这是所有打断的总入口。
2. `reasoning_engine.py::_run_interruptible_planner` —— 请求发起前同理不预设中断 flag。
3. `CycleRuntimeState.reply_sent` + `runtime._turn_reply_sent`：reply 成功置位，
   每个逻辑回合开始重置。

**效果**：她开口之后的后续补充（配表情包、翻记忆再补一句）不会因为对方补一句话而整段作废。

## 5.73 故障判别：网络波动 vs 上游故障（2026-10-28 10:30）

### 教训

2026-10-28 09:59-10:03 出现 18 次「所有模型均尝试失败」，三家供应商（geili / geili2 /
tokendance）同时中招：geili-chat 60 次、geili2-chat 48 次、tokensance-chat 23 次错误。

**当时的判断是「同源波动，建议换上游」——这是错的。**
用户确认：**是本地网络波动**（断网/路由），请求根本发不出去。

### 为什么这个误判很危险

网络故障和上游故障的**日志表现几乎一样**（都是 timeout / connection error /
所有模型失败），但处理方式完全相反：

| | 网络故障 | 上游故障 |
|---|---|---|
| 表现 | 所有供应商同时挂 | 通常单家挂、能切换到备用 |
| 正确处理 | 查本地网络/代理/DNS | 换 key、换供应商 |
| 错误处理 | 换 key（白费钱和时间） | 查本地网络（白查） |

### 判别方法

**看错误类型**：

- `APIConnectionError` / `Connection error` / `getaddrinfo` / `ECONNREFUSED` /
  `ENETUNREACH` → **本地网络问题**
- `APITimeoutError` / `Request timed out`（但连接建立成功）→ 上游慢或挂

**看是否同源**：三家不同供应商同时挂，本地网络问题概率极高（真的全网抖动很少见）。

### 巡检脚本已更新

`health_report.py` 新增 `network` 类别，并在建议里明确区分：

```
if 网络错误 and 上游失败:
    "优先查本地网络（断网/代理/路由），这种情况换 API key 或换供应商都没用"
```

## 5.77 「让她操控电脑没反应、墨迹」根因（2026-10-28 10:50）

### 现象

用户反馈：让她操控电脑时没反应、很墨迹、感觉权限被卡住。

### 排查数据

> 都要用一两句话告诉主人「做了/没做成，因为什么」。调完就沉默是最糟的。
> 如果它提示「主人没明确要求」，就回头问一句「要我用 agent 去做吗？」，别自己反复重试。

**3. 「墨迹」其实不是模型慢**

| 最大 | 120.1s | **19.0s** |
| >30s 次数 | 8 / 39 | **0 / 37** |

## 5.78 agent_talk 改为「主人账号白名单」，去掉关键词匹配（2026-10-28 11:20）

### 为什么要改

「连上了。」，通道完全正常。

**结论：按字面匹配关键词既漏判又折磨使用者，而且安全感是虚的。**

### 新设计

| 项 | 改前 | 改后 |
|---|---|---|
| 判定依据 | 主人 QQ + 最近 4 条消息含关键词 | **只认主人 QQ 账号** |
| 适用范围 | 仅主人私聊 | **私聊 + 群聊都算**（按账号，不按场景） |
| 语义判断 | 代码做字符串匹配 | 交还给她按上下文理解 |

`chat_sessions` 表实测：群聊会话的 `user_id` 全是 `None`，只有私聊才填对端 QQ。
所以不能直接用 `chat_stream.user_id` 判断"是谁在说话"，否则群聊永远不放行。

改法：新增 `_current_speaker_ids()`，从 `message_cache` 的每条消息里取
`message_info.user_info.user_id`（真实发言者），注入：
- `ToolAvailabilityContext.user_id` → 最后一个发言者（决定工具可见性）
- `ToolExecutionContext.metadata["speaker_ids"]` → 本批全部发言者（决定调用许可）

`provider.py` 判定：`speaker_ids` 里**只要包含主人账号**就放行。


学习还有 AI 自检把关（`expression_self_reflect = true`），会评估表达是否贴合场景、是否口语化。

### 问题：私聊用不上

```
[十二月的私聊] 表达方式选择已跳过：本地候选不足，session_id=082dee720be83966...
```

表达候选**按 session 隔离**，私聊没学过东西 → 候选数 0 → 直接跳过。
而 `expression_groups = []` 是空的，没有跨会话共享。

### 修复

```toml
# bot_config.toml → [expression]
expression_groups = [
  { targets = [{ platform = "*", item_id = "*", rule_type = "group" }] },
  { targets = [{ platform = "*", item_id = "*", rule_type = "private" }] },
]
```

**两个关键坑（都踩了）**：

1. **`rule_type` 必须显式写**。`_target_values()` 靠它决定按 `group_id` 还是 `user_id` 匹配，
   缺了直接 `return False`，**整组静默失效**（没有报错）。
2. **group 和 private 要分开两个组**。`rule_type` 是单值，一个 target 只能匹配一类会话。

**`platform="*", item_id="*"` 是代码里的全局共享标记**（`_is_global_expression_group_marker`），
配上后 `has_global_share=True`，查询不再按 session 过滤，直接用全库表达。

### 验证

`get_target_session_ids_with_wildcards` 实测：
- 组0（group）：匹配到 **9 个群**
- 组1（private）：匹配到 **7 个私聊**

> 注意：在独立 Python 进程里测 `_resolve_expression_group_scope` 会得到 False，
> 因为 `chat_manager.sessions` 是运行时内存缓存，独立进程里是空的。
> 必须用 `get_target_session_ids_with_wildcards`（它会查数据库）来验证。

### 效果

私聊现在能拿到全部 592 条表达作为候选，回复会带群友的说话风格。
热重载生效，无需重启。

### 三、几个关键实现决定

**1. 数据源用 `llm_usage` 明细表，不用聚合表。**
`statistics_model_hourly` 由 15 分钟一次的 `StatisticOutputTask` 刷新，**0 点整查它会漏掉最后 0–15 分钟的数据**。
所以插件直接 `sqlite3.connect(f"file:{db}?mode=ro", uri=True)` 只读打开 `data/MaiBot.db`，
WAL 模式下不阻塞主进程写入，也不受聚合延迟影响。

**2. 框架没有 cron，只能自己轮询。**
`maibot_sdk` 确认无 scheduler/interval/cron 组件（只有 Action/Command/Tool/EventHandler/HookHandler 等）。
实现是 `on_load` 里 `asyncio.create_task` 起循环，**每 60 秒醒一次比对日期**，不是 `sleep(86400)`——
长 sleep 在系统休眠/时间跳变后会失准。日界对齐用 `(now - 1day).date()` + 与 `send_at` 比较。

**3. 幂等靠状态文件，不靠内存。**
`data/plugins/deepsleep.daily-report/sent_days.json` 记录已发日期，保留最近 40 天。
插件重载、进程重启都不会重复发。实测：改动后插件热重载两次，数据库里报表消息仍然只有 1 条。

**4. 启动补发（`catch_up_on_start`）。**
如果 0 点那一刻机器人正好在重启，启动 20 秒后会自动补发昨天的报表，不会因为重启丢报。

**5. 缓存命中率的分母是 `prompt_tokens`，不是 `hit+miss`。**
第一版算错了：用 `hit+miss` 当分母得到 54.2%，但按 `prompt_tokens` 算只有 47.7%。
原因是有 **1069 次请求供应商没返回缓存用量**（`hit=0` 且 `miss=0`，共 179 万 prompt tokens），
这部分 token 是按原价计费的（`src/llm_models/utils.py:210-215`：两者都为 0 时全量按 `price_in`）。
漏掉它们会把命中率算虚高。**费用 `cost` 字段是写入时就算好的，直接用，不要重算。**

**6. 手动命令 `/daily_report` 只对主人开放。**
用 `@Command(permission="operator")` + `bot_config.toml` 的 `plugin.command_permissions`：

```toml
[plugin]
command_permissions = { "deepsleep.daily-report.daily_report" = { allow_users = ["qq:100000000"], allow_chats = [] } }
```

实测（`src/core/local_operator.py:65` `has_command_permission`）：
主人在私聊 ✅、主人在群里 ✅、陌生人私聊 ❌、陌生人群里 ❌。
注意 `permission` 只是命令元数据字段，**默认 `public` 意味任何人发 `/daily_report` 都会触发**——
第一版就是这个漏洞，已修。

## 5.86 缓存命中率 47.7% 的完整调查（2026-10-29 01:30）

**问题**：DeepSeek 缓存命中单价 ¥0.01/M、未命中 ¥0.50/M（50 倍价差），实测命中率只有 47.7%。
**要求**：方案必须无副作用。**方法**：账本分析 + 代码核查 + 真实 payload diff + 中转站实测 + 社区调研，五路交叉核实。

### 一、结论先行

**提示词结构本身已经是缓存友好的，问题不在「时间戳/系统提示」这些常见嫌疑上。**
命中率被压低的三大真因，按 token 量排序：

| 因素 | 占未命中比例（估算） | 证据等级 |
|---|---|---|
| 小任务 prompt 天然内容主导（memory 7.3%/learner 1.5%/vlm 2.7%/utils 0.1%） | ~20% | 账本实测 |
| 前缀中段被挖洞：黑话参考消息进出场、图片占位刷新、工具列表增减 | ~30-40% | payload diff 实锤 |
| 上下文压缩重置（head 整体换血）+ failover 跨账号（3.4% 请求） | ~15% | 预览文件计数 + 账本 |
| 真零命中（连 system 都没匹配上，疑似上游高并发下的驱逐/多副本不一致） | ~25-35% | 分布形态推断 |

### 二、五路核实的证据链

**1. 账本（llm_usage，两天样本）**：planner 58.2%（17.3M tokens）、replyer 31.4%（2.5M）、memory 7.3%、learner 1.5%、vlm 2.7%、utils 0.1%。
供应商分布：geili 占 98%+，failover 到 geili2/tokendance 仅 58/1691 ≈ 3.4%。
没回报缓存字段的行只有 30 条（可忽略），**归零是真归零**。

**2. 间隔分析（判别「时间过期」假说）**：同一会话内，planner 相邻请求 <60s 命中 62.7%、1-5min 53.8%、5-30min 48.0%、>30min 31.8%。
replyer 更糟：<60s 归零率 38%，>30min 归零率 81%。**60 秒内也只有 62.7% —— 有个与时间无关的天花板。**

**3. 分布形态（判别「多账号池」假说）**：planner <60s 的命中率分布是
`0-10%: 17% | 40-70%: 19% | 70-90%: 54% | 90-100%: 6%`——不是均匀的（尾部新内容解释的形态），也不是纯双峰，
是「多数请求命中良好 + 一部分整条归零」的混合。replyer 则 52% 整条归零。
归零请求 99% 落在与成功请求相同的供应商+模型上（geili/geili-chat 159 条 vs geili2 仅 1 条）→ **不是 failover 造成的**。

**4. 真实 payload diff（最硬的证据）**：`logs/maisaka_prompt/` 存了每次请求的完整消息序列。
对 群D 群相邻 replyer 请求逐字节 diff（只比真正出网的 role+text，meta 不出网）：
- 有一对在第 **1** 条就分歧（system 后第一条历史换了）→ 压缩触发，历史头部整体换血
- 多对在第 7/10/22/24/27 条分歧。验尸：一条黑话参考消息（「你可以视情况自由使用以下句式…」）
  在上一次请求里存在、在下一次请求里**整个消失**，后续全部前移 → 前缀从该点断裂
- **system prompt（第 0 条）在三条路径各 19 对相邻请求中 0 次变化** —— 系统提示是稳定的，这条洗清了

**5. 中转站实测（花了两分钱）**：用 geili key 发 3300 token 的相同前缀：
- A1 超时，A2 未命中，**A3 命中 93%（cached=3072/3295）**，之后 A5-A8（含两个全新 TCP 连接）全部命中
- 换 geili2 key 发相同前缀 → 未命中（跨 key 不共享，符合 DeepSeek 官方「缓存按用户隔离」）
- **35 分钟后、隔着机器人 15 万 token 真实流量，再发仍命中 93%**
- 结论：中转站**透传缓存字段**、有粘性、不轻易驱逐；但**缓存写入有延迟**（A2 那次明显早于写入生效）

**6. 代码核查**：MaiBot 的 prompt 组装是缓存友好的——system 稳定、历史 append-only、时间戳在尾部（只损失尾部几百 token）、
工具顺序确定。真正会挖洞的点：压缩（每累计 36 条真实消息裁到 6 条）、视觉占位刷新（识图完成后原地改写历史）、
tool_search 发现/折叠 deferred 工具（tools 数组变化）、bot 被新昵称 @ 后 system 变化（低频）。

**7. 社区调研**：DeepSeek 官方确认缓存是前缀精确匹配（从第 0 个 token 开始）、64 token 粒度、按用户隔离、
有效期「几小时到几天」、**对输出质量无影响**（这是「缓存优化无副作用」的官方依据）。
MaiBot 社区：v1.0.12 时代就有 57.7% 的先例（issue #1933），47.7% 接近这个架构的基线；
**v1.3.16 官方发布说明明确优化了「表达与黑话学习」和「记忆」两个模块的缓存利用率**——正好对应我们 7.3%/1.5% 的两大低洼。

### 三、量化：压缩有多频繁

`context_compaction` 预览目录数出来的真实触发次数（近 2 天）：**178 次**。
群D 群一家 110 次 = **每 26 分钟把整个历史前缀连根拔一次**，而它是 token 消耗第一大户（昨天 4.2M）。

### 四、方案清单（按「无副作用」标准筛过）

### 二、为什么会有「聊天 / 识图 / 深度思考」的区分

**它们真的是同一把 key、同一个上游模型 deepseek-v4.1-flash**（`model_identifier` 三处完全相同），

| `geili-vision` | `thinking = disabled`（同为多模态开关） | 仅 vlm（识图）任务 |

也就是说：三个条目共享同一个 base_url + key + 模型标识，**唯一区别是请求体里带不带思考参数**。

## 5.108 重连补拉：重启空窗的漏消息自动回注（2026-11-12 01:25）

**需求**（用户）：短暂重启期间的消息要记得回复，「再问一次不合理」；半夜没人聊天，正是动

  回调推进（`router.on_message_forwarded`）。
- **回放范围**：只补游标里出现过的会话；单会话上限 30 条、时间窗 90 分钟、游标距现在
  <45s 跳过（`[catchup]` 配置节）。
- **自发消息必须显式剔除**：历史接口会返回机器人自发消息，而 live 推送因
  `reportSelfMessage=false` 根本不出现、管线开关默认关闭——不剔除就是自我对话。拿不到
  登录身份时整次放弃。
- **双实例竞争**：插件在两个 runner 各实例化一份（日志可见两条「适配器已连接」），实测
  同批漏消息被回放两遍、库里成对出现。已加跨进程文件锁（`msvcrt.locking`，非阻塞，
  拿不到锁的实例跳过本次）。
- **Host 去重是内存态**（`platform_io/dedupe.py` MessageDeduplicator），不跨重启——回放
  不会被它拦，也因此「已入库但未调度」的消息（如 00:17 那条 @）重放后会重新进入调度。
